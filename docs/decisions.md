## Phase 1
- **Paths:** one `Paths` model (`get_paths`) feeds all Phase 1 code. With `base_dir` the layout is `evidence_raw/`, `evidence_working/`, `db/`, `ledger/`, `runs/` under it. From settings, `base_dir` is the parent of `evidence_raw` (i.e. `data/`), so `vault_path` is stored relative to it with forward slashes.
- **Tamper-evident, not tamper-proof:** hash chain + SQLite `ledger_head` anchor detect edits, deletes, reorders and tail truncation. An attacker who can rewrite BOTH `ledger.jsonl` and `chainofproof.db` can forge a consistent history. Exporting `ledger-head` externally (later: in reports) strengthens it.
- **Append refuses a mismatched anchor:** `Ledger.append` raises if the file end and the anchor disagree, so truncation cannot be hidden by the next append.
- **Hash of an entry** is computed over the raw JSON dict (timestamp as `...Z` string with microseconds), not a pydantic round trip, so verification does not depend on pydantic serialization.
- **Verify reports per-entry problems and resyncs** on the entry's own stored hash/ID, so one tamper yields one message with the ledger ID. A deleted middle entry is reported at the entry after the gap (non-sequential ID); a swap at the first out-of-order ID.
- **Locking:** `ledger.jsonl.lock` with `msvcrt.locking` (Windows) / `fcntl.flock`, plus a per-path `threading.Lock`. The last line is re-read under the lock.
- **Evidence ID allocation** is `MAX+1` in an immediate transaction, before the copy (the ID is in the vault filename). The insert is a separate transaction; the primary key catches a race and ingest cleans up.
- **Rollback:** any failure after the vault copy removes the vault file, deletes the DB row if inserted, and writes `ingest_failed` (best effort).
- **Duplicates** are per `(case_id, sha256)`; the same file in another case is ingested again.
- **Filename sanitizing** is ASCII-only (unicode letters become `_`), capped at 100 chars keeping the extension, leading dots replaced by `_`.
- **Read-only on Windows** is the file attribute; stops accidental edits only. A cleared flag is a `WARN:` problem, not a failure; hash/size/missing are failures.
- **`SourceType`** is a `StrEnum` (ruff UP042); behaves as a str Enum.
- **Case creation** from the CLI is logged to the ledger (`case_create`); `EvidenceStore.create_case` itself does not log.
- **Errors:** expected failures subclass `UserError`; the CLI prints one `error: ...` line and exits 1.
- **Logging in the CLI:** ingest progress and the duplicate notice go through `logging` (RichHandler on stderr).
- **Symlink test** is skipped on this machine (no symlink privilege).
## Phase 2
- **ledger-recover (explicit, never automatic):** `Ledger.recover()` acts only if (1) the chain verifies internally ignoring the anchor, (2) the chain is exactly one entry ahead of the anchor, and (3) the chain entry at the anchor's position has the anchor's `ledger_id` and `entry_hash`. Then it advances the anchor and appends `ledger_recovered` (old/new anchor id and count). Anything else (anchor ahead, hash mismatch, 2+ ahead, broken chain, missing anchor with a non-empty chain) is refused with a one-line "looks like truncation or tampering" message and nothing changes. A healthy ledger is a no-op. `verify` and `recover` share one chain scan (`_scan_chain`).
- **Case logging in the library:** `EvidenceStore.create_case` appends `case_create` (actor `ingest`, details case_id/title) after the DB commit; the CLI no longer logs it. A ledger failure after the commit raises a clear `StoreError` ("case was created but the ledger entry failed"). Previously the CLI actor was `cli`; library calls now use actor `ingest`.
- **Dependencies:** `python-evtx` and `defusedxml` added. python-evtx works on Python 3.12/Windows; the header-only fallback was not needed. All evidence XML goes through `defusedxml` (entity expansion is rejected; tested).
- **Ruff scope:** `extend-exclude = ["data"]`. An earlier `ruff format .` reformatted six vendored files inside `data/downloads` (a metadata notebook and helper `.py` files, no `.evtx`). They were restored from the clone's own git (`git checkout` of exactly those six paths); the clone is clean again and the dataset hashes verify. Lesson: always give ruff explicit paths.
- **Dataset:** commit `4ceed2f4706daf601c212a8f91c113dd85349a2c`. License not verified (a `LICENSE.GPL` is in the repo), so nothing from the dataset is committed except hashes and metadata.
- **Technique verification (expected -> verified):** S1 T1003.001 confirmed (high: Sysmon 10, lsass target, GrantedAccess 0x1010). S2 T1550.002 kept at **medium**: the event is a 4624 type 9 `seclogo` logon, which legitimate `runas /netonly` also produces. S3 expected T1021.002 and/or T1569.002: both kept at medium (ntsvcs pipe, services.exe sets `ImagePath`, services.exe child as SYSTEM; the file has no network logon or ADMIN$ copy, and the payload is a Meterpreter PowerShell stager, not PsExec). S4 T1569.002 high (PsExec pipe pattern + PsExec.exe pipe connect), T1036.003 medium (only the image path `C:\Windows\svchost.exe` shows the rename). S5 T1003.006 high (4662 with replication GUIDs, subject `Administrator`, not a machine account).
- **Host/account mapping:** PC04 and PC01 both map to WS-FIN-07 (S2's file is the pass-the-hash *source machine*, so the same workstation is a consistent story). IEWIN7 maps to SRV-FILE-02 (S3) but also appears in both decoys (WS-HR-03, SRV-WEB-01); aliases are per source so this is unambiguous. MSEDGEWIN10 -> SRV-FILE-02, DC1.insecurebank.local -> DC-01. The DCSync subject `Administrator` and the S2 account `user01` are kept as logged. The S1 Sysmon 10 event has no user field, so GT-ACT-001 has `account: null`.
- **Decoy choice:** candidates in Persistence/Execution with unrelated hosts and tools: `sysmon_13_1_persistence_via_winlogon_shell` (T1547.004), `exec_sysmon_1_lolbin_rundll32_advpack_RegisterOCX` (T1218.011), `persistence_hidden_local_account_sysmon`, `exec_sysmon_1_lolbin_pcalua`. - **Alignment anchor:** the offset is an integer number of seconds chosen so the *floor-second* of the stage's first key event hits the target (S1 09:00:00 ... S5 10:35:00); microseconds are preserved, so the virtual first-event times are 09:00:00.661928 etc. Decoys are anchored on their first record (no key events).
- **Key schema additions:** `GroundTruthContradiction` gets `magnitude_unit` and `params` (machine-checkable exact values) so tests can compare the key with measurements; `SupportingRef.event_id` is optional (synthetic lines have none); `Scenario` carries `virtual_hosts` (hostname, role, IP) and `noise`. Companion files are one per host (3 hosts x 2 kinds) so `source_key` + `seq`/`record_id` identifies a line.
- **P1 targets:** the two PsExec service binaries on SRV-FILE-02 (`PSEXESVC.exe`, renamed `svchost.exe`), because those have real service-install / pipe events to contradict. The synthetic `PSEXESVC.exe` is timed at S3's real service `ImagePath` event even though the real payload is Meterpreter (documented assumption).
- **Key building:** `scenario-keys` (extra command) writes both keys from a fresh generator run; `scenario-verify` rebuilds them and compares byte-for-byte content plus all generated file hashes. YAML is validated through JSON mode so strict pydantic enums load.
- **Security observation:** no event field in the seven files matched the instruction-like pattern (regex for "ignore previous", "system prompt", "you are an AI", "claude"...); `instruction_like_fields` is empty in `inventory.json`. Nothing in the evidence addressed the agent. Note: S3's service `ImagePath` contains a long PowerShell command; it is never stored or printed (key facts keep only short, whitelisted fields).
- **Idempotent build:** `scenario-build` skips ingest for files already in the case (looked up by hash), so a rerun adds no evidence and no ledger entries. `verify-evidence` itself writes integrity entries to the ledger (Phase 1 behavior).
- **Generated files** are `.csv`/`.log`, which ingestion detects as `log_text`.
