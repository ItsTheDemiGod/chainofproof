## Phase 1
- **Paths:** one `Paths` model (`get_paths`) feeds all Phase 1 code. With `base_dir` the layout is `evidence_raw/`, `evidence_working/`, `db/`, `ledger/`, `runs/` under it. From settings, `base_dir` is the parent of `evidence_raw` (i.e. `data/`), so `vault_path` is stored relative to it with forward slashes.
- **Tamper-evident, not tamper-proof:** hash chain + SQLite `ledger_head` anchor detect edits, deletes, reorders and tail truncation. An attacker who can rewrite BOTH `ledger.jsonl` and `chainofproof.db` can forge a consistent history. Exporting `ledger-head` externally (later: in reports) strengthens it.
- **Append refuses a mismatched anchor:** `Ledger.append` raises if the file end and the anchor disagree, so truncation cannot be hidden by the next append.
- **Hash of an entry** is computed over the raw JSON dict (timestamp as `...Z` string with microseconds), not a pydantic round trip, so verification does not depend on pydantic serialization.
- **Verify reports per-entry problems and resyncs** on the entry's own stored hash/ID, so one tamper yields one message with the ledger ID. A deleted middle entry is reported at the entry after the gap (non-sequential ID); a swap at the first out-of-order ID.
- **Locking:** `ledger.jsonl.lock` with `msvcrt.locking` (Windows) / `fcntl.flock`, plus a per-path `threading.Lock`. The last line is re-read under the lock.
- **Evidence ID allocation** is `MAX+1` in an immediate transaction, before the copy (the ID is in the vault filename). The insert is a separate transaction; the primary key catches a race and ingest cleans up.
- **Rollback:** any failure after the vault copy removes the vault file, deletes the DB row if inserted, and writes `ingest_failed` (best effort).
- **Duplicates** are per `(case_id, sha256)`; the same file in another case is ingested again.
- **Filename sanitizing** is ASCII-only (unicode letters become `_`), capped at 100 chars keeping the extension, leading dots replaced by `_`.
- **Read-only on Windows** is the file attribute; stops accidental edits only. A cleared flag is a `WARN:` problem, not a failure; hash/size/missing are failures.
- **`SourceType`** is a `StrEnum` (ruff UP042); behaves as a str Enum.
- **Case creation** from the CLI is logged to the ledger (`case_create`); `EvidenceStore.create_case` itself does not log.
- **Errors:** expected failures subclass `UserError`; the CLI prints one `error: ...` line and exits 1.
- **Logging in the CLI:** ingest progress and the duplicate notice go through `logging` (RichHandler on stderr).
- **Symlink test** is skipped on this machine (no symlink privilege).
## Phase 2
- **ledger-recover (explicit, never automatic):** `Ledger.recover()` acts only if (1) the chain verifies internally ignoring the anchor, (2) the chain is exactly one entry ahead of the anchor, and (3) the chain entry at the anchor's position has the anchor's `ledger_id` and `entry_hash`. Then it advances the anchor and appends `ledger_recovered` (old/new anchor id and count). Anything else (anchor ahead, hash mismatch, 2+ ahead, broken chain, missing anchor with a non-empty chain) is refused with a one-line "looks like truncation or tampering" message and nothing changes. A healthy ledger is a no-op. `verify` and `recover` share one chain scan (`_scan_chain`).
- **Case logging in the library:** `EvidenceStore.create_case` appends `case_create` (actor `ingest`, details case_id/title) after the DB commit; the CLI no longer logs it. A ledger failure after the commit raises a clear `StoreError` ("case was created but the ledger entry failed"). Previously the CLI actor was `cli`; library calls now use actor `ingest`.

- **Hayabusa 4.2.0 CLI differs from older docs:** there is no `csv-timeline` / `json-timeline`; the command is `dfir-timeline`. Exact command (run with cwd = the Hayabusa folder, project-relative paths in the ledger): `hayabusa-4.2.0-win-x64.exe dfir-timeline -f <working copy> -o data/runs/RUN-######/hayabusa_<EV>.jsonl -t jsonl -p verbose -w -K -q -N -U -O -b -r rules`. Profile `verbose` is the smallest profile that has RecordID, Channel, Computer, RuleTitle, RuleID, Level and MitreTags. `-b` (no abbreviations) gives full channel names. `-Q` (quiet errors) was NOT used: with it the 4.2.0 binary exited with -1 before scanning. `-C` (clobber) is not used because every run writes into a fresh run folder. Hayabusa's JSONL also carries `EvtxFile` (a full path with the user name); it is never stored.
- **Rules tree hash:** sha256 over the sorted `relative path NUL file sha256` lines of every file under `tools_bin/hayabusa/rules`, EXCLUDING `.git` (the bundled rules folder is a git checkout; git's internal files change without the rules changing). Computed once per process and cached; the fingerprint (version, exe sha256, rules hash) is appended to the ledger the first time it is used per process/ledger.
- **Two layers (see docs/tools.md):** `events`/`detections` are the agent view; `event_eval_meta` is the eval layer. `tools/query.py` is the only agent-facing reader; a test scans it (and the agent-side packages) for forbidden imports and also imports it in a clean interpreter to prove `chainofproof.eval` / `chainofproof.scenarios` are not loaded transitively.
- **Evidence labels and event ids:** label = `EVTX|FSTL|AUTH` + `-` + first 6 hex of the file sha256 (never a name, path, EV id or source key). Event id = `EVT-` + first 12 hex of sha256(`<evidence sha256>:<locator>`) with locator = EventRecordID for EVTX, `fs:<record_id>` for file timelines, `auth:<seq>` for auth logs. Because the id depends only on file content and locator, identical files (and the same real EVTX in the clean and perturbed cases) get identical event ids across cases; uniqueness is enforced PER RUN (a duplicate inside one file is a hard error) and the primary key is `(norm_run_id, event_uid)`, not `event_uid` alone.
- **Event types table** (channel, EventID -> type): Sysmon 1 process_create, 3 network_connect, 7 image_load, 10 process_access, 11 file_create, 12/13/14 registry_set, 17 pipe_created, 18 pipe_connected; Security 4624 logon, 4672 special_privileges, 1102 audit_log_cleared, 4662 directory_service_access, 4688 process_create_security, 4697 service_install; System 7045 service_install, 104 audit_log_cleared; everything else (including Sysmon 2, 5, 8, 22...) is `other` with its fields kept (sanitized).
- **Field-mapping choices:** image paths keep only the BASENAME in `process_image` / `parent_image` / `target_image`, but the full path stays in `fields` (original key names) so Phase 4 can see masquerading; `Sysmon 13` service names are taken from `...\Services\<name>\...` in the registry target; `logon_id` is lower-cased; IP placeholders (`-`, `unknown`) become null; `UserData` children (Security 1102) are read as fields.
- **Real values in virtual views:** time-looking field values (Sysmon `UtcTime`, `CreationUtcTime`... any value that is exactly a timestamp) are shifted by the source's offset so no 2019/2020 date sits next to a 2024 timestamp; values that are exactly a real computer name (or short name, or machine account `NAME$`, or `DOMAIN\user` with such a domain) are replaced by the source's virtual host. This is part of the alignment layer, not a repair of the planted perturbations. What remains is real content: pipe names such as `svchost-MSEDGEWIN10-8116-stdin` (a pipe name is content and is the pairing field of the synthetic lines). Counts are reported in the phase report; they are not hidden and not failures.
- **Leakage test thresholds:** strict checks on every column (hints `synth_only`, `pair=`, `SYNTHETIC`, `GT-`, original and vault file names, source keys) and on structured columns (real computer names, stage ids, timestamps). A file-system timeline legitimately has file creation times a year or two before the scenario start, so its `timestamp` floor is 2021-01-01; EVTX and auth sources must be 2024-01-01 or later (real captures are 2019/2020).
- **Alignment is per source file** (`tools/alignment.py`): `IEWIN7` maps to SRV-FILE-02 in S3, WS-HR-03 in D1 and SRV-WEB-01 in D2. A computer name without an alias in its file's entry is a hard error, never a silent fallback to the real name.
- **Detections link by (evidence, RecordID, channel):** python-evtx and Hayabusa both report the EventRecordID of the log file, so the pair is unique per file; the channel is compared because Hayabusa abbreviates channel names unless `-b` is passed. Unlinked detections are counted and reported.
- **Migration and backup:** schema version 2 adds `norm_runs`, `events`, `detections`, `event_eval_meta`. Fresh databases are created at v2. `migrate_to_v2` (called by `normalize` and `db-migrate`) first copies the database with the sqlite3 online backup API (the DB is in WAL mode, a raw copy is unsafe) to `data/db/backups/chainofproof.db.pre-v2` (a numbered name if that exists, never overwritten), then migrates in one transaction, then appends a `db_migrate` ledger entry (from/to version, backup file name, backup sha256). A v2 database is left alone (no backup, no ledger entry).
- **Idempotence without deletions:** `norm_runs` holds one row per completed normalization; every read uses "latest completed run per evidence" (`MAX(rowid)` per evidence). Re-normalizing adds rows and files and deletes nothing; two runs on the same evidence produce byte-identical JSONL (canonical JSON, file order).
