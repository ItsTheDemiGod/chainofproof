# Scenarios and ground truth

Scenario `credtheft_lateral_v1`: credential theft, pass-the-hash, lateral movement, a renamed
PsExec service and a DCSync, built from real EVTX captures plus **synthetic** companion files.
Definition, inventory and answer keys live in `scenarios/credtheft_lateral_v1/` (committed).

## Real vs synthetic, in plain words
- **Real:** seven `.evtx` files from the public EVTX-ATTACK-SAMPLES repository (five storyline
  files, two decoys). Nobody on this project generated them. They sit in
  `data/downloads/EVTX-ATTACK-SAMPLES/` and are never modified, moved or committed.
- **Synthetic:** six companion files generated by `scenario-generate`, three per variant
  (a per-host file-system timeline CSV and an auth/network log for WS-FIN-07, SRV-FILE-02, DC-01).
  Each starts with `# SYNTHETIC - generated by ChainOfProof, not real telemetry`. They are NOT real
  telemetry; they exist so there is something to contradict. They are written to
  `data/scenarios_generated/<scenario>/<variant>/` (gitignored).
- The scenario file, inventory and keys are committed; the raw `.evtx` files and generated files
  are not (only their SHA-256 hashes are).

## The alignment layer (why it exists)
The seven real files are independent captures from different machines, years and domains
(`PC04.example.corp`, `PC01.example.corp`, `IEWIN7`, `MSEDGEWIN10`, `DC1.insecurebank.local`...,
2019-2020). To make one storyline we define, per real source, in `scenario.yaml`:
- `time_offset_seconds`: virtual time = real time + offset. The offset is chosen so the stage's
  first key event lands at the planned virtual moment (whole second; microseconds are kept).
- `host_aliases`: real `Computer` name -> virtual hostname.

The layer is **metadata only**. Raw evidence is never altered; Phase 3 normalization applies the
offset and aliases when it builds normalized events. Real account names (`user01`,
`Administrator`, `IEUser`) are kept as they appear in the logs.

## Key-event rules (deterministic, `scenarios/keyevents.py`)
A rule reads one file and returns the 1-5 events that form the attacker action. Rationales name
only the fields used. If a rule finds nothing it returns *unresolved* (confidence low, an honest
note of what the file contains); no event is ever invented.

| Stage | Rule | Techniques / confidence logic |
|---|---|---|
| S1 | Sysmon EventID 10 with `TargetImage` basename `lsass.exe` | T1003.001; high if `GrantedAccess` is a known credential-dumping mask, else medium |
| S2 | Security 4624 with `LogonType` 9 and `LogonProcessName` `seclogo`, else NTLM network logon (type 3, named account); plus the 4672 with the same logon ID | T1550.002; **medium** (type 9 also arises from legitimate `runas /netonly`) |
| S3 | Sysmon 18 pipe `\ntsvcs`; Sysmon 13 by `services.exe` setting a service `ImagePath`; Sysmon 1 with `ParentImage` `services.exe` | T1021.002 medium if pipe seen; T1569.002 medium if service + child seen |
| S4 | Sysmon 17 `svchost.exe` outside `\Windows\System32`; Sysmon 17 pipe `...-<host>-<pid>-stdin/out/err`; Sysmon 18 `PsExec.exe` connecting such a pipe | T1036.003 medium (rename inferred from path only); T1569.002 high when pipe pattern and PsExec connect both appear |
| S5 | Security 4662 whose `Properties` contains a replication GUID (`1131f6ad-...`, `1131f6aa-...`, `89e95b76-...`) | T1003.006; high if the subject is a user account, medium if a machine account |

## The three perturbations (perturbed variant only)
Both variants come from the same seed; the perturbed one differs by exactly these changes, each
recorded as a `GroundTruthContradiction` with exact parameters.

| ID | Kind | What | Magnitude | Detectable by |
|---|---|---|---|---|
| GT-CON-001 (P1) | timestomp | `C:\Windows\PSEXESVC.exe` and `C:\Windows\svchost.exe` on SRV-FILE-02: `si_created`/`si_modified` set to 2021-06-15, `fn_*` keep the real drop time | 2 files (about 1000 days each) | `si` vs `fn` mismatch; creation time disagrees with the real service-install (S3) / pipe (S4) event times |
| GT-CON-002 (P2) | clock_skew | every SRV-FILE-02 auth line shifted +420 s | 420 s | same SMB admin-share connection / logon in the real EVTX (S3) and the auth log, constant offset |
| GT-CON-003 (P3) | log_gap | all DC-01 auth lines in a 12-minute window containing the DCSync event removed; `seq` not renumbered | 720 s window (12 lines in the committed build) | `seq` jump on DC-01 plus real 4662 events inside the window |

Tests measure these properties on the generated files independently and compare them with the key.

## Companion sources
- **File timeline CSV** columns: `record_id, host, path, size, si_*, fn_*, note` (4 timestamps
  each: created, modified, accessed, changed). About 400 benign rows per host. Attacker artifacts
  are timed from real key events: Mimikatz binary 180 s before the S1 event, credential-dump
  output 4 s after, `PSEXESVC.exe` at the S3 service-install event, the renamed `svchost.exe` 3 s
  before the S4 pipe event. Clean: `si_*` equals `fn_*` for attacker files, within 3 s for benign
  ones. Attacker file names are not flagged in `note`.
- **Auth/network log**: one line per event, `key=value`, `seq` +1 per line per host. About 800
  benign lines in total plus lines matching real key events (pass-the-hash logon with the real
  logon ID; SMB `ADMIN$` connection and logon at the S3 time; DCSync replication request with the
  real logon ID).
- Parsers (`scenarios/companions.py`) skip `#` and blank lines and reject malformed lines with a
  line number.
- Noise knobs: `noise.benign_fs_entries_per_host` and `noise.benign_auth_lines_total` in
  `scenario.yaml`. They are part of the scenario (not `settings.yaml`) because the answer-key
  hashes depend on them; change them and re-run `scenario-keys`.

## Limitations
- Companions are synthetic and the timeline is stitched from independent captures: the storyline
  is plausible, not a real incident. S3's real service payload is a Meterpreter PowerShell stager,
  not PsExec itself; the `PSEXESVC.exe` file is a synthetic assumption.
- The EVTX-ATTACK-SAMPLES license has not been verified (a `LICENSE.GPL` file is present), so raw
  files are never redistributed; only hashes and metadata are committed. Re-fetch the dataset at
  commit `4ceed2f4706daf601c212a8f91c113dd85349a2c`; builds and verification fail loudly on any
  hash difference.
- `python-evtx` is used in Phase 2 only for inventory and key-event discovery; production parsing
  is Hayabusa in Phase 3.
- The real S2 file also contains a Security 1102 (audit log cleared) four seconds before the
  logon. It is not used in the key; it is a candidate real anti-forensics signal for Phase 4.
